# Linux connection-churn investigation — 2026-11-07

The symptom in [#303](https://github.com/voidvec/fulla/issues/303)—an accepted connection left unserviced with persistent server CLOSE-WAIT—was **not reproduced in this bounded standalone experiment**. This does not refute the original in-process Fulla observation or establish an upstream fix. Keep #303 open.

## Primary results

A uniform v3 collector completed all 18 cells, three rounds of six configurations, with a 600-second launch window per cell. There were **4,131,146 attempts, zero request failures and zero invalid cells**. Within each cell, all request records had distinct handler counters; the final server counter delta matched every attempt. Across 2,174 snapshots, sampled PID-owned CLOSE-WAIT was zero, and all drained fd counts returned to baseline. Kernel ListenDrops, ListenOverflows and TCPSynRetrans deltas were zero in every primary cell; other retransmission counters were not uniformly zero and remain in the summary.

There were 2,057,463 fresh-mode connections and 72 keep-alive connections (eight per keep-alive cell). No failed request was retried by the probe. Each cell used a new server process, two seconds of startup settling and ten seconds of post-traffic drain. Process shutdown results were recorded separately; all exited with code zero.

The requested rate was a cap of 50 requests/second per worker, eight workers. **Achieved rates were 299.06–395.38 requests/second**, calculated from actual counts and duration. These are standalone ping diagnostics, not IAM throughput, capacity or SLO measurements. No cross-configuration performance ranking is claimed.

## A configuration assumption corrected by source and runtime evidence

For Drogon 1.9.13 on Linux, `ListenerManager::createListeners()` creates one `HttpServer` per IO loop. The Linux `HttpServer` constructor uses Trantor's default `reUsePort=true`. Application `reuse_port=false` adds a startup port-availability check; it does not disable kernel SO_REUSEPORT on these listeners. The fixture read the socket option with `getsockopt()` before listening: **every listener reported SO_REUSEPORT=1 for both input values**. Effective `getThreadNum()`, named IO threads and PID-owned listener counts were also checked.

Consequently, these six configurations do **not** constitute a kernel SO_REUSEPORT on/off experiment. The source's non-Linux cross-loop handoff must not be assumed to describe this Linux listener arrangement. Neither finding identifies the cause of #303. `threads_num` was also confirmed to be a supported legacy configuration key; it was not a configuration bug.

Before the primary run, a collector invoked two full `ss` dumps every five seconds. It completed four valid supplementary cells; a fifth cell and its replacement were invalidated by five-second `ss` timeouts. The 11 failures comprise eight `response_body` records that had received HTTP 200, one `connect`-stage record and two `send`-stage records. All eleven retain endpoint tuples. Stage labels also cover deadline checks between operations; the connect-stage record already has a local/peer tuple, so it is not proof of a failed TCP handshake. In the replacement run the server handled 212,495 of 212,496 attempts; that difference must not be silently discarded. No sampled server CLOSE-WAIT accumulation or retained drained fd was observed in these preliminary runs. User-space stacks were unavailable, so the timeouts cannot be attributed to a particular framework or kernel defect.

To reduce collector overhead, v3 reads the IPv4 TCP table once per periodic sample and joins socket inodes from the server's fd directory. Full `ss` dumps remain at baseline, measurement end, first failure and drain. A periodic socket sample exceeding five seconds or a failed `ss` dump still invalidates a cell. The entire 18-cell primary matrix was restarted uniformly; preliminary failures were not replaced or relabeled as successes. No causal performance comparison between collector versions is made.

## Limits and disposition

- Separate Python clients against a minimal `/ping` server differ from Fulla's in-process Drogon clients, authentication handlers, database/Redis loops and original host. The original transitive-package revisions are not established by this experiment.
- This workload did not achieve the thousands of fresh connections/second suggested in #303. Results apply to the achieved rates above.
- Sampling is nominally every five seconds **plus capture time**; fd and TCP tables are not atomic snapshots. The largest periodic socket collection took 4.960 seconds; the largest gap between consecutive snapshots, including drain, was 10.887 seconds. First-failure capture can wait for the collector lock and is a post-timeout observation, not an instantaneous trace. Short-lived states between samples can be missed; sampled fd peaks are not absolute peaks.
- `gdb` was not installed and kernel stack reads were denied. Thread names, wait channels and epoll fdinfo are present, but these do not replace user-space thread dumps at a real wedge.
- Namespace-wide kernel counters cannot be attributed exclusively to the fixture. A finite drained-fd observation does not prove the absence of a long-term memory or fd leak.

Keep the existing test-side eight-client round-robin keep-alive pool and discard-on-transport-failure behavior in [HttpTestClient.h](../../../../tests/common/HttpTestClient.h). These were verified in source and remain a **test-side mitigation**, not an upstream or production fix. The existing helper has its own retry; the diagnostic probe does not use that helper and never retries a failed attempt. Some individual integration tests still create clients directly, so this is not a claim that every test path is pooled.

Do not change production reuse_port settings or upgrade dependencies on the basis of this negative result. A follow-up reproduction should first match the original host and transitive package revisions and embed the same Drogon client/lifecycle pattern, with usable user-space stack capture and endpoint/inode correlation. File an upstream defect only when that evidence identifies the same symptom. No Fulla runtime changes, dependency upgrades, #300 investigation or issue closure are part of this delivery.
